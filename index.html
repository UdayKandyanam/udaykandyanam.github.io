KubePulse

A CLI that reads a snapshot of a Kubernetes cluster and reports what is failing, the evidence behind each finding, and the next step. It can collect a snapshot from a live cluster through kubectl, diagnose it with eight detectors, and diff two snapshots to show what a fix resolved. Diagnose only: it changes nothing in a cluster.

The same engine also runs as an MCP server: KubePulse MCP wraps the diagnose and diff commands as tools an LLM client can call.

Incident Investigator

A read-only investigator for Kubernetes incidents. It reads a cluster snapshot, scores the likely root cause, and cites the runbook sections behind its diagnosis. It never executes anything: proposed actions are listed as proposals that need human approval, and when the evidence is thin it reports low confidence and names the data that is missing. An evaluation set of eight synthetic incidents scores every change.

LLM agent · Incident diagnosis

Teams Issue-Diagnosis Agent

Outcome: engineers get a diagnosis with concrete next steps inside the Teams thread where they reported the issue.

When a service misbehaves, the first questions are always the same, and the answers live in five different tools. This agent meets engineers where the conversation already happens, inside Microsoft Teams, and does the gathering for them.

An engineer describes the issue in plain language. The agent pulls the platform context around that service, works through the likely causes, and hands back a diagnosis with concrete next steps, instead of a blank search box and a pile of dashboards.

Ask in Teams

The engineer posts the symptom in Microsoft Teams, in plain language, with the service name. No new tool to learn, no ticket form to fill in first.

Under the hood: a multi-step LangGraph workflow. The agent gathers platform context through platform APIs and observability signals, reasons over what it finds step by step, and replies in the thread.

Safety boundary: the agent diagnoses and recommends. It does not change production systems; engineers review the diagnosis and make any changes themselves.

Tradeoff: a chat surface limits how much raw data can be shown, so the agent hands back a worked diagnosis instead of raw logs. In return, adoption costs nothing: no new tool to learn, no new place to check.

Illustrative example

A synthetic exchange in the shape of a real one. The service name is invented; this is not a transcript.

Engineer: claims-api is failing its health checks since the last deployment. What changed?

Agent: Likely cause: memory pressure after the latest deployment; the platform keeps restarting the service. Context gathered: the recent deployment event, the failing health checks, and the service resource signals. Next steps: compare memory limits with the previous release, roll back if the restarts continue, and work through the service health-check runbook.

Platform Knowledge Assistant

Outcome: repeat platform questions answered from internal documentation and runbooks, without interrupting a platform engineer.

Platform teams answer the same questions every week: how a service gets onboarded, where a runbook lives, what a pipeline stage is waiting on. The answers exist, scattered across internal documentation, runbooks, and portal pages.

The knowledge assistant answers platform questions directly from that internal material, so engineers get the procedure, the link, and the context in one reply instead of interrupting a platform engineer or digging through search results.

Under the hood: retrieval over internal platform documentation and runbooks. Answers are grounded in that material and come back with the procedure, the source link, and the context, not model guesswork.

Kubernetes Automation and Platform APIs

Outcome: routine Kubernetes operations became self-service through platform APIs, cutting manual operations by 70%.

Running hundreds of microservices by hand means the same operational tasks repeated daily: provisioning, lifecycle changes, routine cluster operations. Each one is a chance for drift and a slow, manual queue for product teams.

Internal platform APIs, written in Go and Python, turned those recurring Kubernetes operations and service lifecycle tasks into self-service automation that teams call directly.

  • API-first operations: Kubernetes operations and service lifecycle management exposed as internal platform APIs
  • Go and Python automation: the tooling layer platform and product teams build on
  • Production support: deployments, CI/CD, and troubleshooting for Java applications, including Spring Boot microservices on Kubernetes

Tradeoff: the platform team owns an API surface and its support instead of a ticket queue. In return, routine work became consistent and repeatable across teams.
